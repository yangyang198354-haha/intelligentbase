# 本文件是**核对用清单**，不是脚本。每条都要在目标机上**真跑**并留下可复查证据
# （命令 + 原始输出 + 时间），因为本基座最危险的一类事故是「配置写对了、依赖其实没装上」：
#   - bge-m3 的权重未就绪 → Embedder 冷启动失败 → 检索静默降级为「无知识库」，
#     问答照常出答案（fail-open 是产品要求），于是**没人发现知识库其实没接上**；
#   - OCR 引擎未装 → NullOcrEngine 静默接管 → 扫描件文档「成功入库 0 字」，
#     状态是 indexed，看起来一切正常。
# 这两条都不是「报错」，而是「静默降级」。清单的价值就在于把它们从静默变成显式。

#   - 所有 secret 相关命令的输出**不得**带 -v/--show-secrets，不得 redirect 到入库文件。

[A2] 目录与属主（storage 与 snapshots 必须**分开**且均由 qdrant 可写）
    $ ls -ld /var/lib/qdrant/storage /var/lib/qdrant/snapshots

[A3] 端口仅监听回环（**不得** 0.0.0.0）
    $ ss -lntp | grep 6333
    [ ] 显示 127.0.0.1:6333，**没有** 0.0.0.0:6333 或 [::]:6333

    [ ] 与仓库内 unit 一致；is-enabled=enabled；is-active=active

[A5] 文件描述符上限（`LimitNOFILE`）—— 这是最容易漏、且症状最迷惑的一条
    $ systemctl show qdrant -p LimitNOFILE
    [ ] 输出 LimitNOFILE=65536（或更高）
    症状说明：默认 1024 时，集合数量/段文件增长到一定规模后开始
    `Too many open files`，**只在负载上来时才出现**，表现为查询随机 500。
    这也是本清单不写成「看起来没问题就行」的原因。

[A6] 健康检查真跑（不是看 unit 状态，而是看服务真能应答）
    $ curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:6333/readyz
    [ ] 返回 200

[A7] 集合命名前缀核对（隔离是「每项目一个 collection」的硬隔离）
    $ curl -sS http://127.0.0.1:6333/collections
    [ ] 出现的集合名全部形如 `ib_<project_id>_v<version>`
    [ ] 没有任何不带前缀的集合（无前缀集合意味着存在绕过 CollectionResolver 的写入路径）

[A8] 数据目录所在文件系统有余量（向量化是「先建新版本集合再切换」，重建期间会**双份**占盘）

    [ ] 可用空间 >= 现有数据量的 2 倍（重建窗口内新旧集合并存）

[B4] PDF 三路径真跑（用一个**文本层 PDF** 和一个**纯扫描件 PDF** 各测一次）
    说明：清单给**可直接粘贴的真命令**而不是「跑一下解析」——否则执行人各自发挥，
    证据无法互相复核。`ParserRegistry.parse()` 是唯一解析入口（IFC-IB-052），它要求
    显式传入 ocr / renderer / spec，正是为了让「用了哪个 OCR、走了哪条 PDF 路径」
    在调用点就一目了然（默认注册表**不含**兜底解析器：未知扩展名必须报错而非静默吞掉）。

    $ /opt/intelligentbase/venv/bin/python - /path/文本层样本.pdf <<'PY'
      import sys
      from ib.core import ChunkingSpec
      from ib.ocr import RapidOcrEngine
      from ib.parsing import default_registry
      from ib.rendering import PdfiumRenderer

      spec = ChunkingSpec(chunk_size=800, chunk_overlap=100)
      with open(sys.argv[1], "rb") as fh:
          doc = default_registry.parse(
              "pdf", fh, ocr=RapidOcrEngine(), renderer=PdfiumRenderer(), spec=spec
          )
      chars = sum(len(c.content) for c in doc.chunks)
      print("page_count=", doc.page_count, "chunks=", len(doc.chunks), "chars=", chars)
      print("warnings=", doc.warnings)
      PY

    对**扫描件**换文件路径重复同一段命令。判据：
    [ ] 文本层 PDF：chars 明显大于 0，且未触发栅格化/OCR（耗时应在毫秒级，warnings 为空）
    [ ] 扫描件 PDF：触发 pypdfium2 栅格化 + OCR，chars 大于 0
    [ ] 两个样本都拿到非空文本（拿不到 = 该格式静默入库 0 字，而文档状态仍是 indexed）
    提示：若扫描件某页识别为空，按 AC-IB-04-07 是**允许**的（跳过该页 + WARNING，文档仍可
    indexed）。核对时看**整篇**是否为零，并查 `warnings` / 日志中是否确有该页的 WARNING ——
    若整篇为零却没有任何 warning，那是缺陷（静默失败），不是正常降级。

    [ ] 服务 active
    [ ] impl 是 LocalHttpEmbedder（**不是** FakeEmbedder —— 后者只用于离线自测）
    [ ] dim 与配置 `embedding.dim` 一致（bge-m3 为 1024；对不上说明模型与配置不匹配）
    [ ] 冷路径与热路径**都**返回向量（热路径走短超时；若热路径超时而冷路径正常，
        说明 `hot_timeout_s` 对当前硬件过小，问答会被误判降级）
    [ ] 首次冷启动耗时被记录（模型加载慢，冷/热超时值据此确认是否合理）
    说明：端口契约里冷/热是**两个方法**（`embed_documents` / `embed_query`），
    上面的调用刻意把各自超时与重试显式传进去 —— 这两条路径的参数不同正是设计要点

    归属（R3 订正）：`ib-embed` 服务端**已有模块归属** = MOD-IB-26（module_design §1 / §3），

    服务端自身的 `/embed`、`/healthz`、`/warmup`、`/descriptor` 验收按该契约文件
    §3~§9 执行，本清单不重复。（R2 前「只有 systemd 单元与客户端、无模块归属」的表述已作废。）

[B16] 零 Cookie 设置（DR-10）
    $ for p in /healthz /api/files /api/auth/login; do \
        curl -sS -D - -o /dev/null -k "https://<host>$p" | grep -i '^set-cookie:' && echo "HIT $p"; \
      done
    $ grep -c -i 'set-cookie' <(curl -sSI -k https://<host>/api/auth/login)
    [ ] 上述命令对**任意**端点均无 `Set-Cookie`（命中数为 0）
    [ ] 登录成功响应头中也无 `Set-Cookie`（会话令牌只出现在响应体，由前端存 sessionStorage）

    [ ] 目录下**除 `*.pre-rev18.bak*` 外**的每个 `ledger.sqlite3*` —— **凡存在者**（主库，以及服务在跑时
        会出现的 `-wal` / `-shm`）—— mode 均为 **660**（**不是 600** —— 见下方警告块）
    [ ] 上述各文件属主均为 `ib-web`、组为 `ib`
    [ ] `ib-web` 与 `ib-worker` **两个**服务账号**均**属组 `ib`（`id ib-web; id ib-worker` 可复查）
    [ ] `systemctl is-failed ib-worker` 非 `failed`，且上面 `journalctl` 一条不匹配（见下方撤回说明）
    [ ] `llm_key` 为单行表（`CHECK (id = 1)`），全局唯一一个 Key（OQ-IB-26；多供应商 = OOS-18）
    !! 绝不要 chmod 600 !! 台账由**两个**服务账号共享：ib-web 是属主，ib-worker **不是**，
       靠共同组 `ib` 读写。chmod 600 只留属主位 → ib-worker 启动即
       「sqlite3.OperationalError: unable to open database file」；因其单元为 Restart=always，
       表现为**无限重启**，而 ib-web 与 /healthz **全部正常** —— 症状极具迷惑性。
       2026-10-07 生产事故 DEFECT-R18-01 即此因（当时本项写的是 600，且代码把它硬执行了）。
    !! 别漏了 `-shm` !! 台账开 WAL，SQLite 还用同级文件 `-wal` 与 `-shm`；**`-shm` 打开时
       必须读写**，故其 mode 与主库**同等承重**。且**边车的 mode 不由 umask 决定**，而是
       SQLite 在**创建时复制库文件当时的 mode** —— 于是有个顺序陷阱：`sqlite3.connect()`
       早于代码里的 chmod，若那一刻主库还是 600，`-shm` 就被建成 600，此后**只修主文件则
       故障原样复现**。2026-10-07 DEFECT-R18-02 的生产复现正是此形：主库与 `-wal` 已 660、
       `-shm` 停在 600，ib-worker 依旧「unable to open database file」（新版代码已生效、
       主库已修好，故障却一模一样）。
    !! 别把「边车不在」读成失败 !! `-wal` / `-shm` 是**易失**文件：最后一条连接干净关闭时
       SQLite 会 checkpoint 并**删除**它们。故**正常状态**下也可能只看到主库一行。判据因此写成
       「**凡存在者**必须 660」，而非「必须三行俱在」—— 本项原文写死「三行」，2026-10-07 生产上
       照字面读，恰好把一次**正确**的重启判成 FAIL（DEFECT-R18-03）。真正决定性的是下面两条
       服务态 / 日志判据，它们不依赖文件此刻在不在。
    !! 时序：`systemctl restart` 返回 **≠** 装配完成 !! `ib-web.service` 是 `Type=simple`
       （`src/deploy/systemd/ib-web.service:37`），该命令在**进程被拉起**时即返回；而台账由装配期
       `build_llm_key_store` 打开、边车随之创建。2026-10-07 实测：紧接着 restart 跑的 `ls` 读到
       边车缺席（`total 328`），而边车 mtime 显示它们就创建在**同一分钟**，其后读数即为三件套齐备、
       `total 360` —— 同一次正确的重启，两种读数，差别只在查询时机。故先 `is-active`，隔几秒再查。
    !! `*.pre-rev18.bak*` 三行是 600，**这是对的，不要改** !! 它们是 REV-18 迁移前的冷备
       （`ledger.sqlite3.pre-rev18.bak` 及同名 `-shm` / `-wal`），**没有任何服务会打开它**；600 比
       660 **更严**，不违反 REQ-NFR-IB-20。判据已把它排除在外。**但它有个陷阱**：将来若从它
       **还原**，还原出的主库是 600 → **DEFECT-R18-01 / R18-02 原样重演**（新代码下次装配能把主
       文件改回 660，但若 `ib-worker` 先于 `ib-web` 启动，它仍会先撞上打不开）——
       **还原后必须手工 `sudo chmod 0660` 主库**。顺带：该冷备的 `-bak-wal` 为 **0 字节**
       ⇒ 备份当时已 checkpoint 干净，**单独还原那个 `.bak` 主文件即完整**，无数据滞留在 WAL 里。
       验收通过后可将冷备归档或删除（它含一份 Key 密文副本，留着即多一处凭据面）。
    说明：权限位由 `SqliteLlmKeyStore._harden_file_permissions` 在 POSIX 上 best-effort
    收紧至 **0660**（**只去 other 位、保留 group 位**），**主库与两个边车逐个覆盖**；
    chmod 失败会发结构化 WARN（`error_code=ledger_chmod_failed:*` + `kind=db|wal|shm`），
    不再静默吞掉。**属主变更须由用户在部署期执行**。
    机密边界是**两道**：① 目录 `/var/lib/intelligentbase` 与 `/var/lib/intelligentbase/ledger`
    均为 `0770 ib-web:ib` —— 非 `ib` 账号根本无法进入（**主要的一道**）；② 文件 0660
    （目录被误配宽松时的纵深防御）。**注意目录是 `0770`、组员进得去，所以边车自身的 mode
    是承重的，不能靠目录兜底**（本项曾写「边车由第 ① 道兜住」，该论断已证伪）。
    撤回：`sudo -u ib-worker test -r <库文件>` 一法**不再作为判据** —— 2026-10-07 实测它对
    一个**已是 0660、属主 ib-web:ib** 的主文件同样报 FAIL（`$?` = 1），属假阴性；疑因
    `sudo -u` 未携带目标用户的附加组。判据改用上面三条（模式 / 服务态 / 日志），它们不依赖
    sudo 的组语义。如需逐进程复核可改用 `sudo runuser -u ib-worker -- test -r <库文件>`。
    实测：2026-10-07 生产验收 —— 主库与两枚边车均 `-rw-rw---- ib-web ib`（660）、`ib-worker`
    为 `active`、`journalctl -g "unable to open database file"` 零命中；本节各项**全通过**。
