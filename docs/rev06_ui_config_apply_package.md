### 1.1 新增功能需求全文（落到 `docs/requirements_spec.md` §2.7）

#### REQ-FUNC-IB-25 可视化配置界面（定义文档的图形视图，双向同源）

| 字段 | 内容 |
|------|------|
| 描述 | 基座应当提供一套**可视化配置界面**，用于以图形 / 表单方式呈现并编辑项目级**定义文档**（涵盖：专家定义、路由定义、编排定义、工具授权定义）；该界面**只是定义文档的视图**，**定义文档本身是唯一真源**；界面中的编辑结果须能**双向 round-trip** 回写为定义文档，且由定义文档重新载入界面后与视图**语义一致**；界面**不得**拥有独立于定义文档的持久化存储，**不得**形成第二真源 |
| 输入 | 定义文档（唯一真源；项目级、结构化、机器可读）+ 界面中的编辑操作 |
| 输出 | 更新后的定义文档（唯一真源）；与该定义文档等价的图形 / 表单视图；既有派生视图（专家集合、关键词表、默认专家、可委托集合等，见 REQ-FUNC-IB-02）全部由更新后的定义文档**重新派生** |
| 约束 | ①**双向一致（round-trip）**：视图 → 文档 → 视图 不得产生语义漂移；②**单一真源**：界面不得引入独立持久化，派生视图不得手工双写（守住 `agent_platform_research.md` §4.1 风险 R-1）；③**边界声明（与 OQ-IB-04 的关系）**：本条仅覆盖**配置侧**可视化（定义文档的视图，由基座承接并纳入 v1），**问答侧**的完整产品化终端界面**不在本条范围内**（仍见 OOS-06 / OQ-IB-04），配置界面的交付 / 宿主形态属架构阶段问题、本条不作规定；④**凭据不进定义文档**（C-IB-02 / REQ-NFR-IB-07）：定义文档中只出现配置键名、不出现凭据值，界面不得回显凭据；⑤**数据不出本地**（REQ-NFR-IB-08）：界面、其服务与其数据落点须在本地部署环境内，不外发定义文档或文档内容；⑥**部署形态**：须可在**禁 Docker、全物理机直部署、组件裸装**形态下运行（DR-03），不要求任何容器运行时；⑦**框架无依赖**：定义文档的读取与写回层须为纯数据层，不依赖编排框架（对齐 REQ-NFR-IB-11 / REQ-NFR-IB-14） |
| 来源锚点 | 用户裁决（2026-09-27）：诉求③「UI 可视化配置」纳入 v1；`docs/agent_platform_research.md` §3.4 候选点 A（可视化 = 定义文档的视图、双向 round-trip、非第二真源）、候选点 D（与 OQ-IB-04 的边界）、候选点 E（排除项）；§2.1(b)2（Dify 画布 ↔ DSL 同源双视图）、§2.2(b)5（MAF 左 YAML / 右可视化图）、§2.5(b)2（LangGraph Studio Assistants 不改图代码改行为）；§4.1 风险 R-1、§4.3 风险 R-3、§4.5 风险 R-5 |
| 优先级 | Must Have（用户裁决 2026-09-27：诉求③纳入 v1） |

#### REQ-FUNC-IB-26 可视化可编辑对象的边界（节点参数与专家集合，不含运行期改图）

| 字段 | 内容 |
|------|------|
| 描述 | 可视化配置界面的**可编辑对象**应当限定为**节点参数与专家集合**，即：专家的模型与系统提示、专家的工具授权（最小授权范围）、路由关键词与语义范例、路由阈值与边界参数、参与并行 fan-out 的**专家集合**、默认专家标记等；**不包括**运行期增删图节点或改变编排图拓扑 —— 编排图是**编译期结构**（编译一次、进程常驻），其拓扑变更须经定义文档变更并在**装配期重新编译**，不得在运行期由图外输入直接改变 |
| 输入 | 上述可编辑参数集合（取值来自定义文档） |
| 输出 | 更新后的定义文档（唯一真源）；装配期据此重新编译常驻图 |
| 约束 | ①**白名单制**：可编辑参数须有显式清单，清单之外的字段界面**不得写入**；②**图拓扑不可编辑**：节点与边的集合、条件边定义**不是**可编辑对象，运行期改图不在 v1 范围（对齐 `agent_platform_research.md` §2.5(c) 与 §3.3 的顺序原则）；③**不得削弱既有确定性**：路由分类器的确定性温度（temperature=0，REQ-FUNC-IB-19）不得被界面开放为可随意变更；「默认专家恰好一个」不得被绕过（见 REQ-FUNC-IB-27）；④**形状约束**：定义文档中条件边须显式声明其分支映射，否则界面无法正确呈现可达性 —— 界面不得产出无法判定可达性的定义（该经验见 `agent_platform_research.md` §2.5(b)3） |
| 来源锚点 | 用户裁决（2026-09-27）：诉求③「UI 可视化配置」纳入 v1；`docs/agent_platform_research.md` §3.4 候选点 B；§2.5(a)（`StateGraph.compile()` 产出可执行图）、§2.5(c)（把「图结构」做成运行期可改 = 过度设计黑名单）；§3.3 顺序原则（「配置节点参数与专家集合」而非「运行期增删节点」）；§2.5(b)3（条件边须显式 path map，否则可视化会画错） |
| 优先级 | Must Have（用户裁决 2026-09-27：诉求③纳入 v1） |

#### REQ-FUNC-IB-27 可视化配置的完备性校验与装配期 fail-fast 准入闸门

| 字段 | 内容 |
|------|------|
| 描述 | 经可视化配置产生或修改的**定义文档**，在**装配期**（进入编排装配入口前）应当经过**完备性校验**；校验不通过时须**拒绝装配**并给出**可读的、定位到具体条目 / 键**的错误信息；**非法配置不得静默生效**，且**不提供**「强制继续 / 忽略错误」开关。校验须对「经界面编辑」与「直接编辑定义文档」两条来源**一视同仁**（来自界面不构成豁免） |
| 输入 | 定义文档（唯一真源） |
| 输出 | 通过 → 完成装配（图编译一次常驻）；不通过 → 可读错误 + **拒绝装配** |
| 约束 | ①**校验项至少覆盖**：必填项缺失；专家标识 / 面向用户标签的唯一性；**默认专家缺失或不止一个**；路由关键词撞车；工具授权引用了不存在的工具；路由阈值 / 边界参数取值越界；条件边分支映射缺失或不可判定；②**时机为装配期**，不得推迟到首次提问（对齐 REQ-FUNC-IB-01「配置项缺失 / 非法须在启动期可检出」与 REQ-NFR-IB-02）；③**不得削弱「绝不无人应答」的兜底前提**：「默认专家恰好一个」的校验不可被配置或界面绕过（对齐 REQ-FUNC-IB-19 与 §4.2 风险 R-2）；④**错误信息不回显任何凭据值**（C-IB-02 / REQ-NFR-IB-07）；⑤**可离线单测**：校验逻辑须可在无网络、无编排框架环境下单测（REQ-NFR-IB-14 / REQ-NFR-IB-11）；⑥本条**承接** REQ-FUNC-IB-01 / REQ-NFR-IB-02 的既有要求并**具体化到「定义文档 + 可视化编辑」场景**（含校验项枚举与「界面不豁免」），**不构成重复需求** |
| 来源锚点 | 用户裁决（2026-09-27）：诉求③「UI 可视化配置」纳入 v1；`docs/agent_platform_research.md` §3.4 候选点 C；§3.3 P0（「在装配期做『定义合法性』fail-fast」，复用 `validate_specs` 语义）；§4.4 风险 R-4（fail-fast 不得被「宽容导入 + 警告后继续」替代）；§4.2 风险 R-2（守住默认专家兜底）；承接既有 REQ-FUNC-IB-01 / REQ-NFR-IB-02 |

### 1.2 新增用户故事与验收标准全文（落到 `docs/user_stories.md`）

**US-IB-17: 通过可视化界面配置项目定义（定义文档的图形视图）**

- **用户故事**：作为**集成开发者**，我希望通过可视化界面查看并编辑某个项目的定义（专家、路由、编排、工具授权），以便在不直接手写定义文档的情况下完成配置，同时保证定义文档始终是唯一真源、界面与文档不会出现两套不一致的数据。
- **关联需求**：REQ-FUNC-IB-25、REQ-FUNC-IB-26
- **优先级**：Must Have
- **故事点**：[INFERRED — 待开发团队评估]

**验收标准：**

- AC-IB-17-01
  - Given 某项目的定义文档已存在（内容含专家、路由、编排与工具授权定义）且为唯一真源
  - When 集成开发者通过可视化界面修改某专家的路由关键词与系统提示并保存
  - Then 变更被写回**定义文档**（唯一真源）
  - And 由该定义文档重新载入界面后，界面内容与刚保存的编辑结果一致（无漂移）
  - And 系统中不存在任何独立于定义文档的第二份持久化副本

- AC-IB-17-02
  - Given 一份定义文档 D（经界面或直接编辑产生）
  - When 在界面中打开 D 后**不做任何修改**直接回写，得到 D'
  - Then D' 与 D **语义等价**（往返 round-trip 不产生语义漂移）
  - And 逐项比对可编辑对象，无新增、无丢失、无静默改写

- AC-IB-17-03
  - Given 定义文档在界面之外被改动（如由他人直接编辑，或由另一项目的配置覆盖），导致文档与界面当前视图不一致
  - When 界面再次载入该定义文档
  - Then 界面以**定义文档**为准刷新，**不得**用视图内的陈旧副本反向覆盖文档
  - And 不一致或界面无法识别的内容**不被静默丢弃**，而是以可读方式报告（不产生静默分歧）

- AC-IB-17-04
  - Given 可视化界面的可编辑对象清单（专家模型与系统提示、工具授权、路由关键词与语义范例、路由阈值与边界参数、参与并行处理的专家集合、默认专家标记）
  - When 集成开发者在界面中编辑清单内的任一项并保存
  - Then 变更写入定义文档，并在下一次装配后生效
  - And 界面**不提供**运行期增删图节点或改变编排图拓扑的能力
  - And 清单之外的字段不被界面写入

- AC-IB-17-05
  - Given 定义文档中引用了需要凭据的配置项（如外部服务端点）
  - When 审查定义文档与界面的可编辑字段
  - Then 定义文档中**只出现配置键名，不出现凭据值**（凭据一律经环境变量，见 C-IB-02 / REQ-NFR-IB-07）
  - And 界面不回显、不在前端产物中暴露任何凭据值

- AC-IB-17-06
  - Given 可视化配置界面及其服务
  - When 审查其网络行为与数据落点，并核验部署形态
  - Then 定义文档与其内容均留存于本地部署环境，不外发至任何外部服务（REQ-NFR-IB-08）
  - And 该界面可在**禁 Docker、全物理机直部署、组件裸装**形态下运行（DR-03），不要求容器运行时

**US-IB-18: 非法配置在装配期被拒绝（fail-fast）**

- **用户故事**：作为**集成开发者**，我希望配置中的错误在装配阶段就被明确拒绝并给出可读的定位信息，以便我能在服务对外提供问答之前修好配置，而不是等到运行期出现难以排查的异常行为。
- **关联需求**：REQ-FUNC-IB-27、REQ-FUNC-IB-01、REQ-NFR-IB-02
- **优先级**：Must Have
- **故事点**：[INFERRED — 待开发团队评估]

- AC-IB-18-01

  - When 触发装配
  - Then 校验通过并完成装配，编排图编译一次常驻
  - And 变更后的专家集合与路由参数在下一次问答中生效

- AC-IB-18-02

  - When 触发装配
  - Then 装配被**拒绝**，并给出可读的错误信息，**定位到具体条目或键**

- AC-IB-18-03

  - Then 校验**拒绝**该定义文档
  - And 「默认专家恰好一个」的约束不可被配置或界面绕过（这是「任何情况下都不会出现无人应答」的兜底前提，见 REQ-FUNC-IB-19）

- AC-IB-18-04

- AC-IB-18-05
  - Given 定义文档的读取与校验逻辑
  - When 在**无网络、无编排框架**的环境下运行其单元测试

- AC-IB-18-06
  - Given 一份非法的定义文档
  - When 服务启动并执行装配
  - Then 错误在**装配期**即被报出
  - And 不出现「启动成功、直到首次提问才失败」的情形

```text
**US-IB-17: 通过可视化界面配置项目定义（定义文档的图形视图）**

- **用户故事**：作为**集成开发者**，我希望通过可视化界面查看并编辑某个项目的定义（专家、路由、编排、工具授权），以便在不直接手写定义文档的情况下完成配置，同时保证定义文档始终是唯一真源、界面与文档不会出现两套不一致的数据。
- **关联需求**：REQ-FUNC-IB-25、REQ-FUNC-IB-26
- **优先级**：Must Have
- **故事点**：[INFERRED — 待开发团队评估]

**验收标准：**

- AC-IB-17-01
  - Given 某项目的定义文档已存在（内容含专家、路由、编排与工具授权定义）且为唯一真源
  - When 集成开发者通过可视化界面修改某专家的路由关键词与系统提示并保存
  - Then 变更被写回**定义文档**（唯一真源）
  - And 由该定义文档重新载入界面后，界面内容与刚保存的编辑结果一致（无漂移）
  - And 系统中不存在任何独立于定义文档的第二份持久化副本

- AC-IB-17-02
  - Given 一份定义文档 D（经界面或直接编辑产生）
  - When 在界面中打开 D 后**不做任何修改**直接回写，得到 D'
  - Then D' 与 D **语义等价**（往返 round-trip 不产生语义漂移）
  - And 逐项比对可编辑对象，无新增、无丢失、无静默改写

- AC-IB-17-03
  - Given 定义文档在界面之外被改动（如由他人直接编辑，或由另一项目的配置覆盖），导致文档与界面当前视图不一致
  - When 界面再次载入该定义文档
  - Then 界面以**定义文档**为准刷新，**不得**用视图内的陈旧副本反向覆盖文档
  - And 不一致或界面无法识别的内容**不被静默丢弃**，而是以可读方式报告（不产生静默分歧）

- AC-IB-17-04
  - Given 可视化界面的可编辑对象清单（专家模型与系统提示、工具授权、路由关键词与语义范例、路由阈值与边界参数、参与并行处理的专家集合、默认专家标记）
  - When 集成开发者在界面中编辑清单内的任一项并保存
  - Then 变更写入定义文档，并在下一次装配后生效
  - And 界面**不提供**运行期增删图节点或改变编排图拓扑的能力
  - And 清单之外的字段不被界面写入

- AC-IB-17-05
  - Given 定义文档中引用了需要凭据的配置项（如外部服务端点）
  - When 审查定义文档与界面的可编辑字段
  - Then 定义文档中**只出现配置键名，不出现凭据值**（凭据一律经环境变量，见 C-IB-02 / REQ-NFR-IB-07）
  - And 界面不回显、不在前端产物中暴露任何凭据值

- AC-IB-17-06
  - Given 可视化配置界面及其服务
  - When 审查其网络行为与数据落点，并核验部署形态
  - Then 定义文档与其内容均留存于本地部署环境，不外发至任何外部服务（REQ-NFR-IB-08）
  - And 该界面可在**禁 Docker、全物理机直部署、组件裸装**形态下运行（DR-03），不要求容器运行时

**US-IB-18: 非法配置在装配期被拒绝（fail-fast）**

- **用户故事**：作为**集成开发者**，我希望配置中的错误在装配阶段就被明确拒绝并给出可读的定位信息，以便我能在服务对外提供问答之前修好配置，而不是等到运行期出现难以排查的异常行为。
- **关联需求**：REQ-FUNC-IB-27、REQ-FUNC-IB-01、REQ-NFR-IB-02
- **优先级**：Must Have
- **故事点**：[INFERRED — 待开发团队评估]

**验收标准：**

- AC-IB-18-01
  - Given 一份经可视化界面编辑后得到的定义文档，其内容完备且合法
  - When 触发装配
  - Then 校验通过并完成装配，编排图编译一次常驻
  - And 变更后的专家集合与路由参数在下一次问答中生效

- AC-IB-18-02
  - Given 一份定义文档存在非法项（必填项缺失 / 专家标识重复 / 默认专家缺失或不止一个 / 路由关键词撞车 / 工具授权引用不存在的工具 / 路由阈值越界 / 条件边分支映射缺失）
  - When 触发装配
  - Then 装配被**拒绝**，并给出可读的错误信息，**定位到具体条目或键**
  - And 非法配置**不得静默生效**
  - And 系统**不提供**「强制继续 / 忽略错误」开关

- AC-IB-18-03
  - Given 一份定义文档试图移除默认专家，或使其不唯一
  - When 校验执行
  - Then 校验**拒绝**该定义文档
  - And 「默认专家恰好一个」的约束不可被配置或界面绕过（这是「任何情况下都不会出现无人应答」的兜底前提，见 REQ-FUNC-IB-19）

- AC-IB-18-04
  - Given 一份含非法项的定义文档，其中某项以凭据键名形式出现
  - When 校验失败并输出错误信息
  - Then 错误信息指明非法项名（不回显其值）
  - And 错误信息、日志与界面提示中均**不含任何凭据值**

- AC-IB-18-05
  - Given 定义文档的读取与校验逻辑
  - When 在**无网络、无编排框架**的环境下运行其单元测试
  - Then 校验逻辑可被完整单测（覆盖合格样例、各类不合格样例与边界取值）
  - And 被测模块的加载不依赖编排框架（对齐 REQ-NFR-IB-14 / REQ-NFR-IB-11）

- AC-IB-18-06
  - Given 一份非法的定义文档
  - When 服务启动并执行装配
  - Then 错误在**装配期**即被报出
  - And 不出现「启动成功、直到首次提问才失败」的情形
```
