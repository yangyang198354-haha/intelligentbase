## 0. 问题陈述

### 0.1 背景现状（FreeArk 现有实现的只读调研）

FreeArk 已建成一套可工作的「RAG + 多智能体聊天」能力，本项目的输入即是对该能力的一次通用化抽离。其现状（代码锚定）：

**RAG 与向量存储**
- 向量存储：向量以 `numpy float32` 序列化后存 MySQL `BinaryField`，无独立向量数据库。锚点：`api/models_rag.py` L101（`RagChunk.embedding = models.BinaryField`）。
- 检索：进程内 `numpy` 余弦相似度暴力全量扫描，`RagVectorCache.search()` 在内存中对全量向量做归一化点积后取 top-k。锚点：`api/rag_service.py` L104–204（`RagVectorCache`）、L167（`search`）、L182–187（余弦计算）。
- 缓存装载：`load()` 全量从 DB 读入内存，进程级单例（`rag_vector_cache`，L204）；新增/删除后 `refresh()` 起后台线程重载（L157–160）。
- 检索入口：`search_rag(query, k=5, threshold=0.3)`，返回 `{"chunks": [...], "degraded": bool}`，异常一律捕获不外抛（fail-open）。锚点：`api/rag_service.py` L918–935。

**Embedding**
- 生产走**云端 API**，不是本地部署：`RagEmbedder._get_client()` 从 `settings.RAG_EMBEDDING_BASE_URL / RAG_EMBEDDING_MODEL / RAG_EMBEDDING_API_KEY` 构造客户端，默认模型名 `BAAI/bge-m3` 但**经云端 OpenAI 兼容端点远端调用**。锚点：`api/rag_service.py` L285–308；`freearkweb/settings.py` L698–703。
- 另有火山方舟（豆包）多模态 embedding 适配器 `_DoubaoMultimodalEmbeddings`（裸 HTTP，逐条调用、非批量、`data` 为单对象）。锚点：`api/rag_service.py` L209–272；`RAG_EMBEDDING_API_STYLE` 开关，`settings.py` L703。
- 配置项：`RAG_TOP_K`（默认 5）、`RAG_SCORE_THRESHOLD`（默认 0.3）、`RAG_CHUNK_SIZE`（默认 500）、`RAG_CHUNK_OVERLAP`（默认 50）。锚点：`freearkweb/settings.py` L704–707。
- 双路径超时纪律：入库冷路径重试多、超时长；查询热路径重试少、超时短。锚点：`api/rag_service.py` L265–272。

**数据导入与解析**
- 上传 API：`RagDocumentViewSet.create()`，权限 `IsAuthenticated + IsAdminUser`，原始文件读入内存后释放（不落盘），`transaction.on_commit` 起守护线程异步入库，立即返回 201。锚点：`api/views_rag.py` L82–144。
- 上传校验：扩展名白名单 + 50MB 上限 + **文件头字节签名白名单**（`%PDF` / `PK\x03\x04`）。锚点：`api/views_rag.py` L47–54、L57–77。
- 文档台账状态机：`pending → parsing → indexed / failed`，失败带 `error_message` 与 `chunk_count`。锚点：`api/models_rag.py` L23–84。
- 解析器：`.docx`（python-docx，段落合并 + 图片对象 OCR）与 `.pdf`（PyMuPDF，三条路径：页面文字层 / 内嵌 XObject 图片 OCR / 扫描件整页栅格化 OCR）。锚点：`api/rag_service.py` L460（`parse_docx`）、L537（`parse_pdf`）、L612–688（路径 3）、L697（`_ocr_image`）。
- 切分：`_split_text()` 滑动窗口，按 `chunk_size` 切、`chunk_overlap` 重叠，逐 chunk 记录来源定位 `page_or_section`。锚点：`api/rag_service.py` L432–458。
- 图文同 chunk：页面文字 chunk 继承本页代表图（阈值 4KB），修复「问图命中文字却取不到图」。锚点：`api/rag_service.py` L387–430（`_inherit_page_image`）、L391（`_MIN_INHERIT_IMG_BYTES`）。
- 图片落库：`RagImage`（DB BLOB，单图 10MB 上限，`MAX_IMAGE_BYTES` L78），取图端点 `GET /api/rag/images/{id}/`。锚点：`api/models_rag.py` L137–196；`api/views_rag.py` L221–271。
- 管理端点：列表 L96、删除 L147（级联 + 缓存刷新）、重试 L165（仅 `failed` 可重试，需重新上传文件）。
- 前端管理页：`FreeArkWeb/frontend/src/views/KnowledgeBaseView.vue`（拖拽上传、前端类型/大小校验、状态标签、5 秒轮询、失败原因弹窗、重试弹窗）。

**多智能体编排（LangGraph）**
- 图结构：`route → (expert | general) → gate → aggregate → END`，编译一次进程常驻。锚点：`api/langgraph_chat/orchestrator.py` L894–909（`_build`）。
- 并行 fan-out：条件边 `_fan_out` 一次返回多个 `Send`，同 superstep 并发执行多专家，`expert_results` 用 `operator.add` reducer 归并。锚点：`orchestrator.py` L540–560；L127–155（`State`）。
- 路由四级：关键词短路（L508–519）→ 语义高置信短路（L522–529，`semantic_router.SemanticRouter`，τ=0.65 / margin=0.05）→ LLM 分类器 `classify_experts`（`router.py` L277–317）→ 关键词/粘性/域外/默认兜底。护栏 `_guard_against_misroute`（`router.py` L240–274）。
- 专家注册表：`ExpertSpec` dataclass + `EXPERT_SPECS` 列表为**单一真源**，各模块常量由其派生。锚点：`experts.py` L26–82、L88–120。
- 工具桥接：`@tool` 进程内直调，`TOOLS_BY_EXPERT` 按专家最小授权；能力摘要 `build_capability_digest` 由工具表自动派生注入路由提示。锚点：`fa_tools.py` L899–904；`router.py` L191–208。
- 工具-专家委托（深度限 1）；写操作经 `_gate` 的 `interrupt()` 强制确认门。锚点：`orchestrator.py` L93–124（委托工具）、L563–667（`_expert`）、L764–826（`_gate`）。
- 子委托生成打 `INTERNAL_NOSTREAM_TAG` 不外流；融合阶段禁止暴露内部分工。锚点：`adapter.py` L46、L182；`orchestrator.py` L836–852。
- 客户端适配层：`LangGraphAdapter.stream_chat` / `resume_chat`（流式 + 确认恢复）；`related_images` 从终态 State 取出单发。锚点：`adapter.py` L256–260、L397、L230–246。
- 依赖基线：`langgraph>=0.2.50,<0.4`、`langchain-core>=0.3.20,<0.4`、`langchain-openai>=0.2.10,<0.3`。锚点：`FreeArkWeb/backend/requirements.txt` L49–51。
- 编排层已做依赖反转：`langgraph_chat` 对 `api.*` 的依赖仅剩 `adapter.py`（绑定宿主），编排骨架不反向依赖业务。锚点：`orchestrator.py` L195–210。

### 0.2 痛点

1. **专有/闭源依赖**：embedding 依赖云端 API（方舟/火山等），离线不可用、不可控成本、数据出境。
2. **无标准向量存储**：向量以 BLOB 存关系库 + 进程内全量暴力检索，语料增长后内存与延迟线性劣化，无法横向扩展、无索引能力。
3. **不可复用**：RAG 与编排逻辑与 FreeArk 业务（三恒设备、能耗、PLC、业主范围）深度耦合，无法直接服务于新项目。
4. **格式覆盖面不足**：现有上传仅接受 `.docx` / `.pdf`，用户明确要求支持 Markdown 等更多格式。
5. **运维知识不可迁移**：全部配置散落在单一项目的 `settings.py` 与 `.env`，缺少「一份基座接入多个项目」的配置与隔离边界。

### 0.3 本版本目标

把上述能力抽离为一个**独立、通用、开源优先、可本地部署**的基础架构（下称「基座」）：

1. 引入**开源标准向量数据库**（本地部署）承载向量存储与相似度检索，替换「关系库 BLOB + 进程内暴力检索」的存储层。
2. 引入**开源 embedding 模型**（本地部署），以余弦相似度作为向量空间的相似度度量，替换云端 embedding API 依赖。
3. 提供一套 **Web 数据导入**能力，支持 Word / PDF / Markdown 等格式，含可配置的 chunk 切分。
4. 以 **langchain + langgraph** 承载**多智能体编排**（路由 / 并行专家 / 聚合），参考 FreeArk 的实现。
5. 使基座**可被更多项目复用**：配置化接入、专家与工具可插拔、知识库可按项目隔离。
6. 提供**本地部署与运维**能力（服务定义、环境变量、健康检查、日志），目标运行于本地 Ubuntu 主机。

> 说明：本版本**不替换 FreeArk**，不修改 FreeArk 任何文件；FreeArk 仅作为只读参考与代码锚点来源。

#### REQ-FUNC-IB-03 工具注册与能力声明

| 字段 | 内容 |
|------|------|
| 描述 | 基座应当提供统一的工具注册机制：工具按**专家维度**注册（最小授权），并可依据已注册工具**自动派生能力摘要**，供意图路由判断「哪个专家具备处理该问题的能力」 |

## 3. 非功能需求

### REQ-NFR-IB-01 通用性 / 可复用性

基座应当在不修改核心代码的前提下被新项目复用：接入一个新项目所需的改动应限制在「配置 + 新增专家提示文件 + 新增/注册工具」范围内。任何「只有某个业务项目才需要」的逻辑不得沉淀进基座核心。

- 判据：新增一个项目并跑通「导入 → 检索 → 问答」的最小闭环，核心代码改动行数为 0（仅新增配置与扩展点文件）。
- 来源锚点：UB-6；现状参考 `FreeArk:api/langgraph_chat/orchestrator.py:L195–210`（依赖反转，编排层对业务零依赖）、`FreeArk:api/langgraph_chat/experts.py:L9–11`（「加/改一个专家的元数据只需改这一处」）。

### REQ-NFR-IB-02 可配置性

全部可变行为（向量库连接、embedding 端点与模型、切分参数、检索 k 与阈值、路由开关与阈值、专家集合、权限策略、日志级别）应当外置为配置，且：每项有明确默认值；配置缺失/非法时在启动期或首次使用时给出可读错误；不得在代码中硬编码环境相关的值（主机、路径、端口、凭据）。

- 来源锚点：UB-6；`FreeArk:freearkweb/settings.py:L407–446`、`L698–707`（全量配置经环境变量读取并带默认值的既定做法）；`FreeArk:api/langgraph_chat/orchestrator.py:L477–503`（行为开关配置化）。

### REQ-NFR-IB-03 检索性能

检索路径（查询向量化 + 向量库相似度查询）的延迟应当满足交互式问答要求。**规模口径已确认：千级文档量级（几百 ~ 几千份）**（用户决策 2026-09-25，见 DR-05）。

- 量化目标：P95 检索总延迟的目标值**不在需求阶段凭空设定**，须在**目标机（CPU-only + bge-m3 CPU 模式）以千级文档量级实测校准**后确定（分拆为 embedding 推理延迟 + 向量库查询延迟两项）；校准结果作为本需求的验收基线（**校准待部署阶段完成 — 目标机硬件规格 TBD，部署前补实测**）。
- 约束：延迟目标须在**目标机实际算力**下衡量，不得以开发机数据代替；目标机硬件规格（CPU 型号 / 内存 / 磁盘 / 是否含 GPU）尚未实测，本文档一律记为 **TBD（部署前补实测）**。
- 来源锚点：用户决策（2026-09-25）DR-05（规模 = 千级文档量级；架构默认假设 = CPU-only + bge-m3 CPU 模式，GPU 加速留作可选）；FreeArk 现状参考 `FreeArk:docs/requirements/v1.4.0_sanheng_rag/requirements_spec.md:L344–346`（检索延迟 ≤10ms 内存搜索 + embedding ≤3s 的量级参考，**不可直接沿用**，因存储与部署形态均已变更）。

### REQ-NFR-IB-04 入库吞吐与请求响应性

文档解析、OCR、向量化须在**异步**路径执行，不得阻塞上传接口的响应；上传接口的响应时间应当只包含「校验 + 落台账」的成本。单文档端到端入库时长应当有可观测的上限告警（规模口径已确认为千级文档量级；该上限须在目标机上以千级文档量级实测校准后确定，与文档页数、是否 OCR 相关 — **不凭空设定数值**）。

- 来源锚点：UB-3；用户决策（2026-09-25）DR-05；`FreeArk:api/views_rag.py:L136–144`（`transaction.on_commit` + 守护线程后立即 201）、`FreeArk:api/rag_service.py:L902–913`（`start_ingest_thread`）；量级参考 `FreeArk:docs/requirements/v1.4.0_sanheng_rag/requirements_spec.md:L344`（10 页含 5 图的 PDF 端到端 ≤120s，Pi 上）。

## 5. 术语表

| 术语 | 含义 |
|------|------|
| 基座 | 即 intelligentbase 本身：可被多个项目复用的「RAG + 多智能体」基础架构 |
| RAG | Retrieval-Augmented Generation，检索增强生成。先检索知识片段，再由模型据此作答 |
| chunk | 文档切分后的最小检索单元。含文本内容与来源定位元数据 |

| top-k | 检索返回相似度最高的 k 条结果 |

| 专家（expert） | 多智能体系统中的一个角色化智能体，拥有自己的系统提示与工具集，负责某一类问题 |
| 路由（route） | 判断用户问题应由哪些专家处理的决策步骤 |
| fan-out | 一次把同一问题并发分派给多个专家的机制 |
| 聚合（aggregate） | 把多个专家的结论融合为一段面向用户的连贯答复 |
| 工具（tool） | 智能体可调用的函数化能力（如知识检索、数据查询），有名称/描述/参数 schema |
| 委托（delegation） | 一个专家在执行中请求另一个专家协助的机制（本基座参考实现限定深度为 1） |
| OCR | 光学字符识别，从图片中提取文字 |
| fail-open | 依赖故障时返回可用的降级结果而非抛出异常中断主流程 |
| 状态机（文档） | 文档处理状态流转：pending → parsing → indexed / failed |

### 6.1 OD-1 向量数据库选型（优先级：P0）

**决策：Qdrant（CLOSED，2026-09-25）** —— 用户选定；分析师原推荐项亦为 Qdrant，但决策依据为**用户选择**（见 §6.0 DR-01）。

**问题描述**：选用哪一个开源向量数据库作为向量存储与相似度检索的权威实现？评估维度：开源与本地可部署性、生产可用性（持久化、并发、故障恢复）、中文与多语言友好度、运维复杂度（是否需要额外中间件/依赖）、与 langchain 集成的成熟度、许可合规（见 REQ-NFR-IB-12）、目标机算力约束（C-IB-03，见 OD-5）。

| **Milvus** | 功能最完整、生态最成熟、可水平扩展；索引类型丰富 | 组件多（依赖 etcd/对象存储等），运维复杂度与资源占用最高，对单机/低配目标机偏重；**若禁 Docker（OD-3）则部署摩擦显著** |

| **Weaviate** | 内置向量化模块与混合检索；GraphQL/REST 接口完备 | 功能面偏重、内存占用较高；内置模块能力若与"自带开源 embedding"重叠则形成冗余 |
| **Chroma** | 上手最快、与 langchain 集成最紧密、纯 Python 友好 | 定位偏轻量/原型，生产级持久化与并发能力的把握度需实测；大规模语料下的表现存疑 |
| **pgvector** | 若已有 PostgreSQL 则零新增中间件；事务与备份体系复用现有 DB 运维经验；许可友好 | 强依赖 PostgreSQL 这一额外前置组件；超大规模/高并发下的向量检索性能弱于专用向量库；与"开源标准向量数据库"的字面诉求有偏差 |

### 6.3 OD-3 是否允许 Docker（优先级：P0）

**决策：沿用 FreeArk「禁 Docker」（CLOSED，2026-09-25）** —— 全物理机直部署；向量库与 embedding 均**裸装**；**不做容器双路径**。**此项明确为「禁 Docker」，不是分析师原推荐的「折中方案」**（见 §6.0 DR-03）。

**问题描述**：FreeArk 项目明令禁止 Docker（`FreeArk:CLAUDE.md`「禁止 Docker：整个项目采用物理机直接部署，严禁使用 Docker 或任何容器化方案」）。intelligentbase 作为**通用基座**是否继承该约束？此决策直接决定可用的部署形态、依赖分发方式，以及 OD-1 中若干候选（尤其 Milvus）的落地成本。

| 候选项 | 利 | 弊 |
|--------|----|----|
| **禁 Docker（沿用物理机直部署）** ← **用户选定** | 与 FreeArk 现网运维经验一致（`git pull` + 服务重启），团队零学习成本；无容器运行时开销；依赖直接可见、排障路径短；无需处理镜像仓库与网络 | 依赖安装与版本隔离需靠虚拟环境/系统包手工保证，跨项目复用时的环境污染风险高；向量库等组件若多组件依赖（如 Milvus）部署摩擦大；「可复现的交付物」能力弱于容器 |
| **允许 Docker Compose** | 一键拉起向量库等组件、版本与依赖强隔离、交付物可复现、新项目接入成本低（契合 UB-6 的「可复用」诉求）；OD-1 的全部候选均可用 | 与 FreeArk 的既定纪律冲突（若两个项目需共享运维心智，会产生分裂）；目标机需要维护容器运行时；资源开销（OD-5 若为低配机器则放大）；**须确认用户是否愿意在通用基座上放宽 FreeArk 的纪律** |
| **折中：核心服务直部署 + 可选容器化外部组件** ← 分析师原推荐 | 基座本体保持轻依赖直部署；重量级外部依赖（向量库）允许以容器方式作为「可选安装方式」提供，同时提供非容器安装路径 | 需维护两条安装路径，文档与测试成本翻倍；「可选」在实际交付中常退化为单一事实路径 |

**推荐项（决策前建议，已被用户决策覆盖 — 留痕）**：**折中方案**（基座本体直部署 + 向量库同时提供容器与非容器两种安装方式），理由：既尊重 FreeArk 已有的无容器运维心智，又满足 UB-6 对「更多项目可复用」的诉求（不同接入项目的部署环境约束可能不同）。**但该折中方案会引入双路径维护成本，最终取舍必须由用户明确拍板**——本文档不给结论。

**用户决策结果（2026-09-25）**：**未采纳该折中方案**，改为**沿用禁 Docker**，理由是避免双路径维护成本（用户明确给出的依据）。**已评估未采纳**：允许 Docker Compose、折中方案（原因：用户明确选择全物理机直部署、不维护双路径）。

**影响的 REQ**：REQ-FUNC-IB-22、REQ-FUNC-IB-13（OD-1 候选可用范围）、REQ-NFR-IB-10、REQ-NFR-IB-11。

### 6.4 OD-4 聊天 / 多智能体 LLM 是否仍用 DeepSeek（优先级：P0）

**决策：保留云端 DeepSeek（CLOSED，2026-09-25）** —— 须显式声明「用户提问文本 + 检索片段外发云端」；LLM 端点可配置以便未来切本地；**v1 不做本地 LLM 双端**（见 §6.0 DR-04）。

| 候选项 | 利 | 弊 |
|--------|----|----|
| **保留云端 DeepSeek（现状沿用）** ← **用户选定** | 零改动、已验证可用、回答质量有保障、部署资源占用零；实施风险最低 | 用户提问文本与检索到的知识片段会外发至云端第三方，**与「本地部署/数据不出本地」的诉求存在张力**（REQ-NFR-IB-08 需显式声明该例外）；依赖外网与第三方可用性；按量计费 |

| **混合：编排/路由等轻任务用本地小模型，专家答复用云端** | 路由等高频轻任务本地化可降低延迟与成本；核心答复质量不降 | 架构与运维复杂度上升；「部分数据仍外发」使 REQ-NFR-IB-08 的声明更复杂；本地小模型的路由质量须实测（参考实现的路由对模型能力敏感） |

**推荐项（决策前建议，已被用户决策覆盖 — 留痕）**：**保留云端 DeepSeek 作为默认，但在需求文档与部署说明中显式声明该数据外发边界；同时把「切换本地开源 LLM」列为可配置的演进路径**（即基座须在配置层面支持替换 LLM 端点，见 REQ-FUNC-IB-01）。理由：用户仅要求换 embedding，未要求换 LLM，扩大范围有过度设计风险；但 REQ-NFR-IB-08 的例外必须显式化，且基座的可配置性须保证未来切换成本低。**最终取舍请用户拍板**——若用户对数据不出本地有强诉求（例如接入项目涉及敏感文档），则应选本地 LLM 并同步调整 OD-5 的算力要求。
