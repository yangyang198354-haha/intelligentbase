## 执行摘要

- **业务背景（用户原文）**：「除了 kb-agent 以外，现在还需要一个可以给所有项目使用的顾问 agent，顾问 agent 默认是一个客户，能够专业有礼貌地回答客户的问题。对于专业的知识，他可以调用 kb-agent 查询 RAG，对于通用的信息，它可以使用 WebSearch 或者 WebFetch 这样的工具在互联网检索。后回答。并且它在一个会话中能保留上下文记忆，能够正确理解上下文的意思，包括话题的变化。能够精准识别意图，也能派发给其他 agent。并且把结果收拢总结答复。这个 agent 要加到这个编排系统中，以后新建项目也能决定用不用这个 agent，或者使用 agent-builder 对他进行微调。或者对多个 agent 进行编排。」；「先整理我的需求，写成用户故事。确认后再开始开发。」

- **核心结论（现状核实，详见§现有系统基线）**：(1) 现状下 agent 之间**不能互相调用**，派发只能由 route 节点完成——按用户裁决（D-03）顾问**不需要**"agent 调用 agent"能力，而是"顾问 → 路由 → 被委托 agent → 回到顾问汇总"的编排式委托；但编排图不允许环、同一专家只能对应一个 agent 节点（`src/ib/config/graph.py:133`、`:198`），"回到顾问"的实现方式交架构 ADR（C-R28-08）；(2) 唯一内置工具是 `search_knowledge`，**没有任何联网工具**，工具执行无超时；(3) DAG 路径下 agent 只收到当前问句，**看不到会话历史**，历史只用于路由粘性。因此"顾问调用 kb-agent / 派发其他 agent / 多轮记忆 / 联网"四块都是**新能力**，不是配置层面的调整。
- **2.1.0 修订**：落点 CL-003（AQ1~AQ5）。REQ 条数不变（18 + 11）；[INFERRED] 仍为 0 ÷ 29 = 0%（本次所有改动均有用户裁决来源，无新增推断）。
- **3.1.0 修订**：落点 CP-003（D-07）。搜索提供方 = DeepSeek 官方 Search API（画像 P11-3）；新增 REQ-FUNC-019（替身提供方生产禁用）；其余 Q1 / Q2 / Q4 / Q5 的落点见修订记录。优先级沿用既有规则：Q3 属用户裁决新增项 → Must Have（REQ-FUNC Must 17 / Should 2）。
- **用户裁决（1.1.0）**：OQ-R28-01 笔误，默认面向客户的顾问角色；OQ-R28-02/03 按用户原话改为编排式委托；OQ-R28-07 生产可出网；OQ-R28-08 搜索服务为可替换外部服务、复用优先。**仍待补充**：评测集数据（OQ-R28-12）。
