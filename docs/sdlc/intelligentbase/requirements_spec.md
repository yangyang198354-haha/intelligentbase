## 执行摘要

- 业务背景：用户原文「资料管理页面目前只能通过选择文件上传一个文件，我希望能够上传一个文件夹，整个文件夹都能上传上去。而且这些文件能够有文件目录一样管理……就像云盘一样。当然，这些文件都要可以索引到向量库。而且文件可以更新，更新后会重新索引。每个文件也可以看到上传时间或者索引成功的时间。」
- 规模：功能需求 17 条（REQ-FUNC-001 ~ 017）/ 非功能需求 7 条（REQ-NFUNC-001 ~ 007）/ 约束 6 条（C-01 ~ C-06）。
- INFERRED：0 条，占比 0 ÷ (17 + 7) = 0/24 = 0%，不超过上限 20%（画像 P5 `inferred_max`）。1.0.0 中的 4 条（REQ-FUNC-016、REQ-FUNC-017、REQ-NFUNC-002、REQ-NFUNC-006）已由用户在 CL-008（2026-10-24，原话「确认，按照推荐」）确认，来源改写为"[INFERRED]→用户确认 CL-008"，**不再计入**推断（原 4/24 = 16.7%）。
- 来源口径：PM 草稿 US-1 ~ US-14 中标"推断"的条目（US-2/7/11/12/13/14）已由用户答复 CL-002（2026-10-24）确认，来源写"PM 草稿 US-N，用户确认 CL-002"，不计为 [INFERRED]。
- 优先级规则：用户给出了 US-1 ~ US-14 的优先级（Must/Should/Could），照用；其余新增条目中，来自用户答复 CL-003 ~ CL-006 的为 Must Have，本文档自行补充的条目按其重要性标 Must/Should（见各行）；CL-008 确认后优先级不变。按此规则 REQ-FUNC：Must 13 / Should 3 / Could 1；REQ-NFUNC：Must 5 / Should 2。
- 与基线的关系（基线只读，不修改）：本文是对 `docs/requirements_spec.md`（v1.13.0）中 REQ-FUNC-IB-48（项目域资料上传）及 REQ-FUNC-IB-04/05/06/07/08/24/32 的**增量**。新编号 REQ-FUNC-NNN / REQ-NFUNC-NNN 按协议 §I 起新序列，与基线 `REQ-FUNC-IB-NN` 族互不冲突。
- **基线冲突登记**（1.1.0 通读基线后新增，详见 B-14、C-06）：基线 OOS-07 把"同名文档覆盖、多版本共存、版本回滚"列为范围外；本增量的 REQ-FUNC-008（更新）与 REQ-FUNC-011（覆盖）在**同名覆盖/更新**这一点上取代 OOS-07，**多版本共存与版本回滚仍排除**（OOS-N02）。
