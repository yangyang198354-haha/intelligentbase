**US-IB-01: 通过 Web 界面导入文档**

- **用户故事**：作为**知识库管理者**，我希望通过 Web 界面上传业务文档并指定它属于哪个知识库，以便系统自动完成解析与入库，供后续检索使用。
- **关联需求**：REQ-FUNC-IB-04、REQ-FUNC-IB-05、REQ-FUNC-IB-09
- **优先级**：Must Have
- **故事点**：[INFERRED — 待开发团队评估]

**验收标准：**

- AC-IB-01-01
  - Given 知识库管理者已登录且有该知识库的管理权限
  - When 其上传一个符合格式与大小约定的文档并指定知识库
  - Then 接口在文档落台账后立即返回成功，返回体含文档 id、文件名、大小与状态
  - And 返回时该文档状态为 `pending` 或 `parsing`
  - And 上传请求的响应不等待解析与向量化完成

- AC-IB-01-02
  - Given 知识库管理者在上传界面
  - When 其选择一个不在允许格式白名单内的文件
  - Then 前端在浏览器侧拦截并给出可读提示，不发起上传请求
  - And 即使绕过前端直接调用接口，服务端也返回 4xx 与可读错误信息
  - And 数据库中不新增任何文档台账记录

- AC-IB-01-03
  - Given 知识库管理者在上传界面
  - When 其选择一个超过大小上限的文件
  - Then 前端在浏览器侧拦截并给出可读提示，不发起上传请求
  - And 服务端对超限文件同样返回 4xx 且不落台账

- AC-IB-01-04
  - Given 一个文件的扩展名声明为允许格式，但其文件头字节签名不属于该格式（伪造扩展名）
  - When 该文件被上传到接口
  - Then 服务端返回 4xx 与可读错误信息
  - And 数据库中不新增任何文档台账记录

- AC-IB-01-05
  - Given 一份包含文字的合法文档已成功上传
  - When 后台解析与向量化流程完成
  - Then 该文档状态变为 `indexed`
  - And 其 chunk 数大于 0
  - And 导入界面列表中该文档显示为「已入库」状态并展示 chunk 数

- AC-IB-01-06
  - Given 导入界面中存在状态为 `parsing` 的文档
  - When 页面处于打开状态
  - Then 页面按固定周期自动刷新列表状态
  - And 当列表内不再存在非终态文档时，自动停止刷新

**US-IB-02: 诊断并重试失败的文档处理**

- **用户故事**：作为**知识库管理者**，我希望看到文档处理失败的原因并能够重试，以便在依赖临时故障（如 embedding 服务不可用）后无需重新走一遍人工流程即可恢复。
- **关联需求**：REQ-FUNC-IB-04、REQ-FUNC-IB-08、REQ-FUNC-IB-09
- **优先级**：Must Have
- **故事点**：[INFERRED — 待开发团队评估]

**验收标准：**

- AC-IB-02-01
  - Given 一份文档因任一步骤异常而处理失败
  - When 知识库管理者查看该文档
  - Then 该文档状态为 `failed`
  - And 界面提供「查看原因」入口，展示可读的失败原因文本
  - And 失败原因文本包含可定位的步骤信息，不含凭据等敏感内容

- AC-IB-02-02
  - Given 一份文档状态为 `failed`，且导致失败的依赖已恢复
  - When 知识库管理者触发重试并提供重试所需的源文件
  - Then 接口返回成功，该文档状态重置为非终态
  - And 失败原因被清空
  - And 上一次失败遗留的切分块被清理，重试完成后 chunk 数不出现重复累加
  - And 重试成功完成后状态为 `indexed` 且 chunk 数大于 0

- AC-IB-02-03
  - Given 一份文档状态为 `indexed`（非 `failed`）
  - When 知识库管理者对该文档触发重试
  - Then 接口返回 4xx，错误信息中说明「仅失败状态可重试」并回显当前状态
  - And 该文档的数据不被改动

- AC-IB-02-04
  - Given 一份文档正在处理中（状态为 `parsing`）
  - When 该文档在此刻被管理操作删除
  - Then 后台处理任务检测到文档已不存在并安全退出
  - And 服务不产生未捕获异常、不中断其他任务

**US-IB-03: 管理与下架知识库文档**

- **用户故事**：作为**知识库管理者**，我希望查看知识库中的文档清单并删除过期或错误的文档，以便检索结果始终基于当前有效的资料。
- **关联需求**：REQ-FUNC-IB-06、REQ-FUNC-IB-07、REQ-FUNC-IB-16
- **优先级**：Must Have
- **故事点**：[INFERRED — 待开发团队评估]

**验收标准：**

- AC-IB-03-01
  - Given 知识库中已有若干文档
  - When 知识库管理者打开导入界面
  - Then 列表展示每份文档的文件名、大小、上传人、状态、chunk 数与上传时间
  - And 列表排序是确定性的（同一时间创建的多条记录顺序稳定，不出现刷新后乱序）
  - And 列表响应中不包含向量数据或文件内容

- AC-IB-03-02
  - Given 知识库中存在一份 `indexed` 文档，共 N 个 chunk
  - When 知识库管理者确认删除该文档
  - Then 接口返回成功
  - And 该文档台账记录被删除
  - And 其全部切分块与向量被一并清理，不留下孤儿数据
  - And 列表中该文档消失

- AC-IB-03-03
  - Given 一份 `indexed` 文档已被删除，且索引一致性已达成
  - When 终端提问用户提出与该文档内容高度相关的问题
  - Then 检索结果**不包含**来自该已删除文档的任何片段
  - And 系统如实反映「未找到相关内容」，不得凭陈旧数据作答

- AC-IB-03-04
  - Given 知识库管理者尝试删除一个不存在的文档 id
  - When 其发起删除请求
  - Then 接口返回 404
  - And 界面给出相应错误提示

**US-IB-04: 导入多格式文档（Word / PDF / Markdown 等）**

- **用户故事**：作为**知识库管理者**，我希望导入 Word、PDF、Markdown 等不同格式的业务文档，以便不必为了入库而手工转换格式。
- **关联需求**：REQ-FUNC-IB-10、REQ-FUNC-IB-11（图片 OCR，已确认纳入 v1）、REQ-FUNC-IB-12
- **优先级**：Must Have
- **故事点**：[INFERRED — 待开发团队评估]

**验收标准：**

- AC-IB-04-01
  - Given 知识库管理者上传一份包含多个段落的 Word（.docx）文档
  - When 处理完成
  - Then 文档状态为 `indexed`，chunk 数 ≥ 1
  - And 每个 chunk 的来源定位字段包含可读的段落地标（如「段落 3」）
  - And 纯文字 chunk 的来源类型标记为非图片

- AC-IB-04-02
  - Given 知识库管理者上传一份 PDF 文档
  - When 处理完成
  - Then 文档状态为 `indexed`，chunk 数 ≥ 1
  - And 每个 chunk 的来源定位字段包含可读的页地标（如「第 3 页」）

- AC-IB-04-03
  - Given 知识库管理者上传一份 Markdown（.md）文档，含多级标题与段落
  - When 处理完成
  - Then 文档状态为 `indexed`，chunk 数 ≥ 1
  - And 每个 chunk 的来源定位字段包含可读的位置地标（如标题层级或段落序号）
  - And 切分结果不出现空内容 chunk

- AC-IB-04-04
  - Given 知识库管理者上传一份不在支持列表内的格式的文件（如 .xlsx）
  - When 服务端处理该文件
  - Then 该文档状态最终为 `failed`
  - And 失败原因明确说明「不支持的文件类型」，不含模糊表述
  - And 其余已入库文档不受影响

- AC-IB-04-05
  - Given 新增了一种文档格式的解析能力
  - When 该格式被加入支持列表
  - Then 上传接口与入库主流程无需修改即可接受该格式
  - And 该格式的解析实现不改变既有格式的解析结果

- AC-IB-04-06
  - Given 知识库管理者上传一份 PDF，其中某页既无文本层又无可提取的内嵌图片（典型扫描件 / 图纸页）
  - When 处理完成
  - Then 该页经整页渲染后执行 OCR，OCR 产出的文本作为切分块的来源参与向量化与检索
  - And 该块的来源类型标记为图片来源，来源定位包含页码
  - And 该文档最终状态为 `indexed`（不因该页为扫描页而 `failed`）

- AC-IB-04-07
  - Given 一份文档内含承载文字的图片（如 .docx 内嵌截图）
  - When 处理完成
  - Then 图片中的文字被提取并参与切分与向量化
  - And 当 OCR 引擎不可用时该图片被直接跳过并记录 WARNING，不导致文档 `failed`
  - And 单张图片 OCR 失败只跳过该图，不影响该文档其余内容入库
  - And OCR 依赖已在目标机上真装真跑验证（见 AC-IB-12-04）

**US-IB-05: 配置 chunk 切分策略**

- **用户故事**：作为**知识库管理者**，我希望调整切分的块大小、重叠量等参数，以便针对不同业务的文档特点（如密集参数表 vs 长段落说明）获得更合适的检索粒度。
- **关联需求**：REQ-FUNC-IB-12
- **优先级**：Should Have
- **故事点**：[INFERRED — 待开发团队评估]

**验收标准：**

- AC-IB-05-01
  - Given 一份总字数大于 chunk 大小的纯文本
  - When 使用当前默认参数切分
  - Then 相邻 chunk 之间存在配置声明的重叠量
  - And 切分不在段落内部强制切断，除非单段落本身超过 chunk 大小（此时该段落走滑动窗口）
  - And 切分结果中不存在空内容 chunk

- AC-IB-05-02
  - Given 切分参数（块大小 / 重叠量）被修改为新值
  - When 新文档被导入
  - Then 新文档按其内容与**新参数**切分
  - And 参数生效范围明确（对已入库文档的影响见 AC-IB-05-03）

- AC-IB-05-03
  - Given 已入库文档是在旧切分参数下切分的
  - When 切分参数被修改
  - Then 系统明确说明已入库文档**不会被自动重新切分**
  - And 若需要使新参数对既有文档生效，存在可触发的重建路径（其形态见 REQ-FUNC-IB-24 / US-IB-16 / OQ-IB-01）

**US-IB-06: 接入开源本地向量数据库**

- **用户故事**：作为**集成开发者**，我希望基座使用一个开源、可完全本地部署的向量数据库来存储与检索向量，以便摆脱专有关联库 BLOB 存储与进程内暴力检索的局限，并可按项目需要选择实现。
- **关联需求**：REQ-FUNC-IB-13、REQ-FUNC-IB-14、REQ-FUNC-IB-16
- **优先级**：Must Have
- **故事点**：[INFERRED — 待开发团队评估]

**验收标准：**

- AC-IB-06-01
  - Given 向量数据库（**Qdrant**，单实例、非容器裸装直部署 — 用户决策 2026-09-25）已按配置部署并连通
  - When 一份文档完成向量化
  - Then 其每个 chunk 的向量与元数据（知识库标识、文档标识、内容、来源定位、来源类型）被写入向量数据库
  - And 写入结果与该文档的 chunk 数一致

- AC-IB-06-02
  - Given 向量数据库中已有多个知识库的数据
  - When 针对知识库 A 发起检索
  - Then 返回结果**仅**来自知识库 A
  - And 知识库 B 的数据不出现在结果中

- AC-IB-06-03
  - Given 向量数据库进程或所在主机被重启
  - When 服务恢复后发起检索
  - Then 重启前已入库的向量仍可被检索到
  - And 无需重新解析或重新向量化

- AC-IB-06-04
  - Given 一份文档的向量已写入
  - When 该文档被删除
  - Then 其全部向量被从向量数据库中移除
  - And 删除操作可按文档维度精确执行，不误删其他文档的向量

- AC-IB-06-05
  - Given 某向量数据库实现被替换为另一实现
  - When 仅修改配置与对应的客户端适配
  - Then 上传、检索、编排等上层模块无需改动
  - And 既有自动化测试（含替身实现）仍可全部通过

**US-IB-07: 部署并接入开源本地 embedding 服务**

- **用户故事**：作为**集成开发者**，我希望基座使用开源、本地部署的 embedding 模型产出向量，并以余弦相似度作为相似度度量，以便摆脱云端专有 embedding 依赖，同时保证向量空间口径一致。
- **关联需求**：REQ-FUNC-IB-15、REQ-FUNC-IB-14
- **优先级**：Must Have
- **故事点**：[INFERRED — 待开发团队评估]

**验收标准：**

- AC-IB-07-01
  - Given embedding 服务（**bge-m3**，本地部署、CPU 模式，仅使用其稠密向量能力 — 用户决策 2026-09-25）已在本地按配置就绪
  - When 一份文档入库
  - Then 其 chunk 被批量向量化，产出的向量维度与配置声明的维度一致
  - And 入库过程中**不产生**对任何云端 embedding 服务的调用

- AC-IB-07-02
  - Given 同一段文本
  - When 分别通过「批量路径（入库）」与「单条路径（查询）」向量化
  - Then 两条路径产出的向量在同一相似度口径下自相似度约为 1（差异在数值精度容差内）
  - And 检索所用的相似度分值与向量空间口径一致（余弦相似度）

- AC-IB-07-03
  - Given 入库冷路径与查询热路径使用不同的超时与重试参数
  - When 本地 embedding 服务响应变慢（如首次加载模型）
  - Then 入库路径按较长的超时与较多的重试继续等待，不轻易将文档判为失败
  - And 查询路径按较短的上界超时快速失败并转入降级（见 US-IB-14）

- AC-IB-07-04
  - Given embedding 模型的许可类型已知（**bge-m3**，已随 OD-2 关闭确认）
  - When 评估该模型可否用于本项目
  - Then 文档中记录其许可类型与结论
  - And 若许可对商业化或分发有限制，则给出替代方案或明确的使用边界

- AC-IB-07-05
  - Given 目标部署机的算力情况（**架构阶段默认假设：CPU-only + bge-m3 CPU 模式；GPU 加速留作可选；硬件规格 TBD，部署前补实测** — 用户决策 2026-09-25，DR-05）
  - When 核验已确认的 embedding 模型（**bge-m3**）在目标机上的可用性

- **关联需求**：REQ-FUNC-IB-24（已确认要，用户决策 2026-09-25，DR-07）、REQ-FUNC-IB-08、REQ-FUNC-IB-16
- **优先级**：Should Have
- **故事点**：[INFERRED — 待开发团队评估]

**验收标准：**

- AC-IB-16-01
  - Given 知识库中已有 N 份 `indexed` 文档，且 embedding 模型或向量维度已按配置变更
  - When 知识库管理者触发索引重建（范围：全量 / 指定知识库 / 指定文档）
  - Then 系统对范围内的文档重新解析 / 重新向量化并写入向量库
  - And 重建完成后检索返回的向量来自新模型 / 新维度
  - And 重建过程无需知识库管理者重新上传原始文件（前提：原始文件已持久化 — 见 OQ-IB-01）

- AC-IB-16-02
  - Given 一次索引重建被中断（进程退出 / 服务重启）
  - When 重建被重新触发
  - Then 重建可重复执行且幂等，不产生重复切分块或重复向量
  - And 已完成部分的重复处理不改变最终结果

- AC-IB-16-03
  - Given 重建正在进行
  - When 终端提问用户发起检索
  - Then 系统的行为被明确定义（可接受降级或双写过渡），不出现查询挂起或返回混合维度导致的错误
  - And 该期间的检索行为在文档中有明确说明

- AC-IB-16-04
  - Given 重建范围内某份文档处理失败
  - When 重建流程继续
  - Then 该文档被标记为 `failed` 并给出可读原因
  - And 其余文档的重建不受影响

**US-IB-18: 非法配置在装配期被拒绝（fail-fast）**

- **用户故事**：作为**集成开发者**，我希望配置中的错误在装配阶段就被明确拒绝并给出可读的定位信息，以便我能在服务对外提供问答之前修好配置，而不是等到运行期出现难以排查的异常行为。

  - Then 校验通过并完成装配，编排图编译一次常驻
  - And 变更后的专家集合与路由参数在下一次问答中生效

- AC-IB-18-02
  - Given 一份定义文档存在非法项（必填项缺失 / 专家标识重复 / 默认专家缺失或不止一个 / 路由关键词撞车 / 工具授权引用不存在的工具 / 路由阈值越界 / 条件边分支映射缺失）
  - When 触发装配
  - Then 装配被**拒绝**，并给出可读的错误信息，**定位到具体条目或键**

  - When 校验失败并输出错误信息

- AC-IB-18-05
  - Given 定义文档的读取与校验逻辑
  - When 在**无网络、无编排框架**的环境下运行其单元测试
  - Then 校验逻辑可被完整单测（覆盖合格样例、各类不合格样例与边界取值）
  - And 被测模块的加载不依赖编排框架（对齐 REQ-NFR-IB-14 / REQ-NFR-IB-11）

- AC-IB-18-06
  - Given 一份非法的定义文档
  - When 服务启动并执行装配
  - Then 错误在**装配期**即被报出
  - And 不出现「启动成功、直到首次提问才失败」的情形

- **用户故事**：作为**终端提问用户**，我希望答复在生成过程中就逐步呈现、而不是等整段生成完才一次性返回，并希望在完成时同时拿到本次答复所依据的来源清单，以便更快看到进展、并能自行核验引用。

  - And 收到的全部内容片段按序拼接后与最终答复一致（不丢字、不重复、不乱序）

  - And 调用方显式启用该能力后，两类片段以**可区分的事件类别**分别推送

  - Then 事件流中**不包含**任何内部子任务的中间生成内容
  - And 内部产物在交付前被过滤或显式标记为内部，**绝不**作为面向用户的内容片段出现
  - And 终端用户不因内部产物看到重复内容或半成品（如同一段答复出现两次、或出现被截断的半句）

  - Then 系统**不推送空的内容片段**，且**不臆造**任何引用来源
  - And 该次交互仍以一个**明确的收尾事件**结束（恰一次），调用方可据此终止等待，不出现悬挂的连接
  - And 该收尾事件的事件类别与正常完成一致，或可被调用方识别为终态

**US-IB-20: 会话生命周期（会话隔离 / 状态丢失安全失败 / 可选确认中间态与恢复）**

- **用户故事**：作为**终端提问用户**，我希望每次提问的上下文都限定在我自己的会话内，并且在系统重启或状态丢失时**宁可安全失败、也不要默默替我执行**；作为**集成开发者**，我希望基座提供「需人工确认的中间态」这一**可选机制**（默认不启用、不绑定我的业务语义），并允许会话在恢复时携带确认决策，以便把写操作确认这类交互接进我自己的业务。
- **关联需求**：REQ-FUNC-IB-20（并关联 REQ-FUNC-IB-23 多项目隔离；REQ-NFR-IB-02 可配置性）
- **优先级**：Must Have（由分析师评定 —— 会话隔离与「丢失=安全失败」属正确性约束；判定依据见本文档附录 E 的 REV-11 自检）
- **故事点**：[INFERRED — 待开发团队评估]

**验收标准：**

- AC-IB-20-01
  - Given 同一基座实例内存在会话 A 与会话 B（可分属不同项目 / 知识库）
  - When 会话 A 中的用户提问并产生答复与结构化产物
  - Then 会话 B 的事件流中不出现会话 A 的任何内容片段、结构化产物或上下文
  - And 会话 B 的答复不受会话 A 历史的影响（默认口径：**会话内隔离、不跨会话注入**，见 OQ-IB-08，该口径仍保持开放）
  - And 会话标识要么被服务端认可、要么被明确拒绝——**不存在**「标识非法即静默新建或落默认会话」的行为

- AC-IB-20-02
  - Given 基座对会话状态的**持久化策略**（进程内 / 外部持久化）已在配置与部署文档中**显式声明**（见 REQ-NFR-IB-02）
  - When 包含待确认中间态的会话在状态丢失后（如服务重启）被继续使用
  - Then 系统**不得**在缺失该状态的情况下静默续跑对应的中间态
  - And 该次交互以**安全失败**（fail-closed）方式结束：明确告知需重新发起或重新确认
  - And 不出现「确认尚未作出、动作却已执行」的情形

- AC-IB-20-03（子子句：可选手动确认中间态 —— 机制存在 / 默认不启用 / 不绑定业务语义）
  - Given 通用基座本身不携带任何具体业务的确认语义
  - When 考察基座是否具备「需人工确认的中间态」能力
  - Then 基座**提供**该机制（可由接入业务按需启用），且**默认不启用**
  - And 该机制**不绑定**任何具体业务动作的确认语义（「哪些操作需要确认」由接入业务决定，基座不内置该判断）
  - And 未启用时问答流程不产生任何确认等待，其行为与不存在该机制时一致（不引入额外阻塞）

- AC-IB-20-04（子子句：确认中间态的呈递与决策回传）
  - Given 接入业务已显式启用确认机制，且某次执行到达需确认的中间态
  - When 该中间态被呈递给用户、且用户作出决策
  - Then 用户能将该状态与正常答复片段区分开（明确感知「正在等待确认」）
  - And 收到决策后，执行**自该中间态继续**，而非从头重跑整段流程
  - And 未收到决策时，执行保持在中间态，**不擅自继续执行**该待确认动作

- AC-IB-20-05（子子句：会话恢复携带确认决策 + 重启丢弃待确认状态 = 安全失败）
  - Given 一个会话在待确认中间态被中断（进程退出 / 服务重启）
  - When 该会话被恢复
  - Then 若恢复请求**携带确认决策**，系统据此**自该中间态继续**执行
  - And 若**未携带**确认决策，或该会话的待确认状态已在重启中丢失，系统**不得**静默续跑该待确认动作，而以**安全失败**结束并提示重新发起
  - And 「重启丢弃待确认状态」为**既定语义（fail-closed）**，不得被实现为「默认放行 / 默认视为已确认」

- AC-IB-20-06
  - Given 会话标识带项目 / 知识库归属，且基座按项目隔离数据（REQ-FUNC-IB-23）
  - When 以归属 A 的会话标识恢复一个属于 B 的会话，或提交一个非法 / 伪造的会话标识
  - Then 系统拒绝该请求或以安全失败结束，**不返回** B 的会话状态
  - And 不出现跨项目 / 跨知识库的会话状态泄漏
  - And 拒绝行为可被调用方识别（不静默地当作新会话处理）

**来源与口径（REV-11，仅新增故事适用；不改既有条目格式）**
